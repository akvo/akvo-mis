# Feature Design Document: Bars Measured by a Number Question

**Task ID**: VIZ-015.b
**Author**: Iwan
**Date**: 2026-09-08
**Status**: Implemented, in the VIZ-015 PR (#349). 608 backend tests and 435
frontend tests across 49 suites pass; flake8, eslint and prettier clean.

---

## 1. Context & Problem Statement

```
Currently:
- Every bar and every stack segment is a COUNT of submissions or sites
- A number question can only be the bars' subject, never their height:
  handle_option_question counts Answers rows and has no value column
- So "how many projects per agency" is expressible and "how much money
  per agency" is not

Goal:
- Let an option-question bar be measured by a NUMBER question — sum of
  project cost, average household count — instead of a row count
- Reuse the aggregation that already exists rather than inventing one
```

VIZ-015 deferred this explicitly, and it has now been asked for:

> **Stacking a number-valued bar.** A bar whose value is an average or sum
> of a number question, split by an option question, is a real request and
> a different computation.

The three controls then read as a standard chart builder — dimension,
measure, breakdown:

| Control | Example | Role |
|---|---|---|
| **Category** (`question`) | The project is meant for? | the bars |
| **Value** (`value_question`) | Project cost | the bar height — empty means count |
| **Split each bar by** (`stack_by`) | Implementing agency | the segments |

The aggregation machinery is already in place. `AGG_FUNCS` covers average,
sum, max, min and last, and `Repeat aggregation` already exposes them for
number questions. What is missing is the **pairing**: an option question
for structure with a number question for magnitude.

---

## 2. Requirements

### User Acceptance Criteria

- [x] A bar measured by an option question can take an optional **Value**
      question, and its bars then show that question's aggregate
- [x] Only number questions are offered as the Value
- [x] Leaving Value empty keeps today's behaviour exactly — a count
- [x] The aggregation (sum, average, max, min, last) is the author's choice
- [x] The chart says what it is measuring, so a reader does not mistake a
      cost total for a project count

### Technical Acceptance Criteria

- [x] `value_question_id` is accepted only alongside an option-typed
      `question_id`; with a number question it is redundant and refused
- [x] It must be a `number` question on the widget's own form
- [x] **Sum is refused when the stacking question is multi-choice** (D-1)
- [x] **Percentage requires `repeat_agg=sum`** — refused under every other
      aggregation, because none of them leaves a total to divide by (D-2)
- [x] **`include_unanswered` / `include_empty` are refused outright**, at
      any aggregation: their bucket counts sites, and these bars are
      totals (D-2)
- [x] It is refused with a cross-form stack (out of scope, §11)
- [x] Absent `value_question` produces byte-identical responses to today
- [x] A cell with no answers to the Value question is 0, not absent

## 5. Decision Log

### D-1: Full value to each selected option, and Sum refused with a multi-choice split

**Options Considered**:
1. Attribute the full value to every selected option, but **refuse Sum**
   when the stacking question is multi-choice
2. Attribute the full value to every selected option, always
3. Split the value evenly across the selections

**Decision**: Option 1.

**Rationale**: The hazard is not uniform across aggregations, which is
what makes a single blanket rule wrong.

For **Average, Max, Min and Last**, full attribution is *correct*.
"Average project cost among projects involving the Water Authority" is a
sound statistic, and every project involving them belongs in it.

For **Sum** it is not. A $10,000 project naming three agencies would
contribute $10,000 to each, so the bar totals $30,000 — and a stacked bar
reads as a partition of a whole. Nobody misreads an inflated count;
everybody misreads a budget total.

Option 3 was rejected because it invents an attribution the form never
recorded — no project ever cost $5,000 — and it makes Average meaningless.
Option 2 was rejected because "the chart is not a partition, do not read it
as one" is not something a chart can say.

**Impact**: One refusal in the serializer and in `validate_widget`, and the
aggregation list narrows in the picker when the split is multi-choice. It
is the same shape as VIZ-015's D-1: refuse the combination that produces a
plausible-looking wrong number rather than document it.

**The same overlap exists for a multi-choice *category*, and is not
refused.** A project serving Villages and Settlements adds its full
household count to both bars, so summing across bars overstates. The rule
targets the split rather than the category deliberately: within one bar a
stacked chart *performs the addition itself*, so the bar height is visibly
wrong, while separate bars are only wrong if a reader adds them up
mentally. Refusing the category case too would forbid "total households by
what the project serves", which is a chart people legitimately want. The
distinction is between a number the chart computes and one the reader
might.

### D-2: Percentage requires Sum over a Value question

**Options Considered**:
1. Refuse `value_type=percentage` while a Value question is set
2. Normalise each bar against its own summed total
3. Allow it only where a total of the same quantity exists

**Decision**: Option 1 first, then **Option 3** after review.

**Rationale**: A percentage needs a denominator that is a total of the
same quantity as the numerator, and most of the percentage paths divide
by a **submission count** — `qs.count()` on the plain option bar,
`len(submission_ids)` for a multi-choice stack. Against a value cell that
is money over rows: meaningless, and it looks fine. That is what Option 1
was protecting.

But one denominator is a real total: `sum(cells)`, the bar's own sum. So
under `repeat_agg=sum` the chart reads exactly as asked — *"of the
households this agency serves, 85% are under an approved plan"*. Under
average/max/min/last it does not, because a sum of averages is not a
quantity, which leaves only the count denominators again.

The rule composes with D-1 rather than adding a condition: Sum is already
withheld from a multi-choice split, so "percentage requires sum" cannot
reach the `len(submission_ids)` denominator.

**Impact**: `Show as: Percentage` survives in the Value type list only
while the aggregation is Sum, and moving off Sum snaps the value type back
to Count. Both validators enforce the same pairing.

**Second refusal, from the same audit**: `include_unanswered` /
`include_empty` cannot be combined with a Value question **at any
aggregation**. They append a "No information available" bucket counting
*parents* to a chart whose other bars are sums of a number question, and
they swap the percentage denominator for a parent count. A row of sites
cannot join a chart of households. The builder disables the coverage
switch while a Value is set, and clears it when one is picked.

### D-3: The Value question lives on the widget's own form

**Options Considered**:
1. Same form only
2. Allow the registration parent's number questions too

**Decision**: Option 1, matching VIZ-015's rule for the stack question.

**Rationale**: Reading a value across the parent link is the VIZ-015.a
join, and that join is defined for counting sites, not summing values —
see §11. Keeping the Value on the widget's own form means the aggregate
runs over exactly the submissions already in scope.

## 6. Type/Constant Mappings

| Config | Query parameter | Meaning |
|---|---|---|
| `value_question` absent | — | Count submissions (today's behaviour) |
| `value_question: <id>` | `value_question_id` | Aggregate that question |
| `repeat_agg` | `repeat_agg` | Which aggregate — already exists |

`repeat_agg` is reused rather than duplicated. It already means "how to
combine several numbers into one" for repeatable groups, and it means the
same thing here; a second control saying `Sum / Average` beside it would
be two names for one idea.

## 7. Implementation

Four compute paths count rows today, and each needs a value variant. Three
shared helpers keep the change from being four separate rewrites:

```python
def value_by_data(value_question, data_ids):
    """{data_id: [values]} for the value question, or None."""

def aggregate_values(values, agg):
    """One number from many, per AGG_FUNCS' vocabulary. Empty -> 0."""

def cell_value(data_ids, values_by_data, agg):
    """len(data_ids) when there is no value question, else the
    aggregate. The one branch that makes counting and measuring the
    same code path."""
```

`cell_value` is why "absent value question is byte-identical" is a
structural guarantee rather than a claim to re-test: the counting answer
is `len()` of the very list the old counters were counting.

Then, at each place a handler currently does `+= 1`, it collects the
submission's data ids instead and calls `cell_value` at the end:

| Path | Chart |
|---|---|
| `_option_group_by_option` | unstacked bars |
| `_stack_option_by_period` | stacked by month or date |
| `_stack_option_by_parent` | stacked by site |
| `_stack_option_crosstab` | the cross-tab |

`_stack_option_by_parent` is the awkward one: it issues a `COUNT` per
(parent, option) pair rather than bucketing in Python. It moves to the
same fetch-once-and-bucket shape as the others, which is a small
performance win independent of this feature.

### The four controls, once a Value is set

| Control | With a Value question |
|---|---|
| Value | number questions of the widget's own form; empty means count |
| Repeat aggregation | relabelled **Combine values by** — it is no longer about repeat groups |
| Value type | Percentage only while the aggregation is Sum (D-2) |
| Include sites with no data yet | disabled, and cleared when a Value is picked (D-2) |

The value-type control needed one thing the decision log did not predict.
D-1 withholds Sum from a multi-choice split and D-2 requires Sum for
Percentage, so **together they can make Percentage unreachable** — the
list is simply one entry shorter, with nothing to say why, and an author
reasonably concludes the feature is broken. A hint beneath the control
names whichever condition is unmet: the multi-choice split when that is
what blocks Sum, otherwise the aggregation itself.

## 8. Compatibility

- [x] Absent `value_question` takes every existing code path unchanged
- [x] No stored widget carries the key, so every published dashboard is
      byte-identical
- [x] Mobile unaffected — dashboards are web-only

## 9. Security

`value_question` is an integer resolved through the ORM and validated
against the widget's own form. `allowlist_from` must collect it, exactly
as it collects `stack_question`, or a public dashboard will refuse to
serve its own widget.

---

## 10. Testing Strategy

| Layer | What |
|---|---|
| Compute | Each of the four paths with a Value question, against hand-counted sums and averages |
| Compute | Absent Value question returns byte-identical rows to today |
| Validation | Every refusal: non-number Value, wrong form, Sum with a multi-choice split, percentage without Sum, `include_unanswered`, cross-form |
| Validation | Percentage **accepted** under Sum, and its rows adding to 100 — otherwise the refusals alone would pass with the feature switched off |
| Public | `value_question` reaches the allowlist |
| Frontend | The Value control appears only for option questions; the aggregation list narrows for multi-choice splits; the value-type list keeps Percentage only under Sum |

---

## 11. Out of Scope

- **Cross-form (VIZ-015.a) with a Value question.** The join adds 1 per
  site in the browser; summing would need the value per site in the
  response and a rule for which submission's value a site contributes
  when it has twelve. Refused for now, deliberately, rather than half
  answered.
- **Percentage under average/max/min/last.** D-2 — allowed under Sum.
- **A coverage bucket beside value bars.** D-2's second refusal.
- **A Value question on the parent form.** D-3.
